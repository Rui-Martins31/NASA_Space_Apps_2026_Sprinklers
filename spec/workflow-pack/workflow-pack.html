The Workflow Pack

Nine skills for shipping real work with AI agents: how to scope it, build it, test it, review it, and know when it’s actually done.

Hand the agent a lot of rope — a terse instruction and an issue number is often the whole spec — and hold a small number of gates that never move.

  • A regression test is provably red before the fix and green after.
  • A claim of “it works” needs real output behind it. “Did you run it?”
  • Docs are the source of truth, not paperwork written afterward.
  • Every unit of work gets an independent review before it’s called done.
  • Ask before guessing on anything genuinely open.

Almost everything else — how the work organises itself internally, which agent does what, which recommended option wins — matters much less than people think.

Three ideas worth stealing

Even if you take nothing else from this page.

The unchecked box

In a change request, - [ ] Manual smoke test — not done from this environment is worth more than any amount of prose. A silent gap looks complete; the reviewer finds out in production.

“I can’t see this from the repo”

The biggest way clarifying questions fail: an agent offers four reasonable options, and all four are wrong, because the real answer is infrastructure only the human knows about. Before offering a multiple choice, ask whether the answer could live outside the repo. If it might, ask openly instead.

Verify the reviewer, not just the implementer

A reviewer reporting “2 pre-existing test failures” when there are 5, plus a flaky 6th it never saw. A review pass producing 6 findings of which 1 survives checking. Reviewers are agents too, with the same failure modes.

The loop

/delivery-loop

The order work ships in, and the gates between the steps.

One issue. One branch. One change request.

Throughout: "change request" means whatever your tracker calls the reviewable unit of change — an MR on GitLab, a PR on GitHub / Azure DevOps. The mechanics live in your tracker's interface skill (glab on GitLab — see /using-glab; the equivalent CLI elsewhere), which is the default flavor in the examples below.

This is the sequence work ships through. Each step points at the skill that owns its detail — this skill owns the order, and the gates between steps. The steps aren't ceremony: each one catches a class of failure the next step can't.

The sequence

get latest
  → branch per issue
  → implement (read the docs first)
  → full suite + typecheck + lint
  → open the change request (closes the issue)
  → independent review
  → conflict-check against main
  → mark ready → merge
  → switch back to main, pull, drop the branch
  → verify it's actually live

1. Start from an issue

If there isn't one, write one first — see /scoping. The issue is what makes the work small enough to execute unattended, and it's what the change request closes.

One issue = one branch = one change request. If the work doesn't fit that, it's two issues.

2. Get the latest — before you read anything

git fetch, then confirm you're actually current, before reading code or planning. A stale checkout wastes the whole loop: a shared checkout once sat 88 commits behind origin/main, and the research done against it described a file structure that no longer existed. Everything downstream of that was wrong and nobody noticed until the change request.

Check you're current first. It costs one command.

3. Branch per issue

Branch off an up-to-date main, named for the work:

git switch main && git pull
git switch -c fix/<n>-<short-slug>      # or feat/, docs/, chore/, test/

Isolation is the point: an abandoned attempt costs nothing, and main always stays shippable. Never commit straight to main — even for a one-liner, even when you're sure.

Never mix two issues on one branch. It sounds efficient and it isn't: the change request becomes un-reviewable, the Closes #N trailer can only be honest about one of them, and if one half needs reverting you can't. If you find a second bug while working, file it (/scoping) and leave it.

When you're ready for more: worktrees. Once branches are second nature — and especially once you're running several agents at once — git worktree gives each branch its own directory, so parallel work can't collide and you never stash to switch tasks. Swap step 3 and step 9 for worktree equivalents when you get there. Nothing else in this loop changes.

One hazard, if you do: never cd to the main checkout from inside a worktree session — not even briefly, not even to "just compare." A cd <main> && git stash -u really did stash someone's untracked files in their real checkout. Some harnesses reset the working directory after the command already ran there: the reset protects the next command, it doesn't undo the one that just ran. If you need pre-change state, use git show <ref>:<path> or git diff <ref> -- <path> — read without mutating another working tree.

4. Implement

Read the relevant docs before writing code, not only update them after. Docs state authoritative conventions and gotchas the code alone doesn't reveal — and they're the source of truth, so a divergence is a bug to reconcile, not a judgment call you get to make alone.

Update the docs in the same change. Not a follow-up. See /review-gate lens 2.

Follow the simplicity ladder for anything you add — /review-gate owns it, rung 1 ("does this need to exist at all?") through rung 7 ("the minimum code that works"). The most common slop is reimplementing what already lives a few files over.

Test during the build, not as cleanup → /test-design.

5. Full suite + typecheck + lint

Run the project's full suite, typecheck, and lint before the change request — not just the tests you touched.

  • Scope lint runs to the files you changed, not the whole repo.
  • If there are pre-existing failures, prove they're pre-existing — check the same commit on main and say so explicitly. Never let someone else's red blur into yours; that's how a real regression hides.
  • Cite the real command you ran and the real count, here and in the change request.

6. Open the change request

Open it as a draft, and have it close the issue.

  • /good-mr owns the description — the summary, the test plan, and the honest disclosure of what you did not verify.
  • Your tracker's interface skill owns the mechanics (heredocs, flags, the escape hatch for what the CLI can't express). /using-glab is the GitLab one; on GitHub / Jira / Azure DevOps it's that tool's CLI.
  • /commit-message owns the commits underneath it.

7. Independent review — before merge

→ /review-gate. Spawn a separate agent; an implementer reviewing its own diff shares its own blind spots.

This step has a known failure mode: on long sessions it quietly lapses because nobody restated it. A lapse is a bug in the process, not an acceptable shortcut. Apply it to every unit of work, every time.

Post the review to the change request when your tracker's CLI is available — a review that lives only in a session transcript is invisible next week.

8. Conflict-check, mark ready, merge

  • Get the latest changes from main again and conflict-check before merging.
  • A draft change request refuses to merge. Mark it ready first — on GitLab that's glab mr update <n> --ready, then glab mr merge <n> --yes; other trackers have the same ready-then-merge two-step in their own CLI.

9. Clean up

Get back to a clean starting point, so the next task doesn't inherit this one's mess:

git switch main && git pull
git branch -d fix/<n>-<short-slug>      # -d, not -D: it refuses if the work isn't merged

Use -d deliberately. It's a safety net — if it refuses, your work isn't actually merged and you want to know that now rather than after you've deleted it. (Deleting the source branch on merge — --remove-source-branch on GitLab, the equivalent toggle elsewhere — handles the remote side.)

Leaving old branches around is how you end up starting work on a stale base three weeks later.

10. Verify it's actually live

Green tests are necessary, never sufficient. If the change has to land in a deployed environment, check it there: use argocd for sync status and pod logs, hit the real endpoint, load the real page.

"Did you run it?" is the reflex to internalize. A claim of "it works" needs real output behind it. If you couldn't verify something, say so plainly — "not verified from this environment" is a respectable line. A silent gap is not.

The engagement contract

Who gets interrupted, and when:

  • Scoped work (a named issue, a reported bug) gets one terse instruction and **full autonomy. Engage at kickoff and the merge decision** — not in between. Don't ask for status approval mid-loop on work that's already well-scoped; just run the loop.
  • Ambiguous or greenfield work gets a plan reviewed before any code → use /extensive-interview rather than guessing and building.
  • A blocked action is a decision, not a transient error. If a merge (or anything else) is blocked by a permission gate, stop and ask. Do not retry it, and do not reroute through a different command to achieve the same effect — an agent once retried a blocked destructive git command via another command. That's the anti-pattern, and it's worse than the original block.
  • Queue follow-up work rather than waiting serially. Prefer being notified when background work finishes over polling it.

Anti-patterns

  • Planning or reading code against a stale checkout.
  • Branching off a main you never pulled.
  • Committing straight to main because it was "just a one-liner".
  • Two issues on one branch, because they were both small.
  • Writing code before reading the docs for the area you're touching.
  • Leaving docs for a follow-up change request that never comes.
  • Letting pre-existing failures blur into yours instead of proving which is which.
  • Merging without an independent review because the session got long.
  • Trying to merge a draft, then treating the refusal as a mystery (it tells you the fix).
  • Retrying or rerouting a blocked action instead of stopping and asking.
  • Calling it done because the suite is green, without ever running the real thing.
  • Leaving merged branches lying around, then branching off one of them next month.

Before you build

/extensive-interview

Extract what you need, and force your assumptions into the open.

The most expensive bug is a wrong assumption nobody said out loud.

This skill extracts what you need to build the right thing, and — just as importantly — forces the assumptions you're already making into the open where they can be corrected cheaply.

When to run it

  • Project inception — greenfield, no spec yet.
  • A big architectural pivot — the shape of the solution is genuinely open.
  • A critical new domain — the rules are the product, and getting them wrong is expensive.
  • Mid-task, when you hit an ambiguity or a fact that doesn't add up.

For scoped work (a named issue, a reported bug), don't run this — use /scoping instead.

The mode gate — read this before you ask a single question

Default to extensive. Then check the docs:

  1. Do the docs already answer it? → Don't interview. Ask the small gap-filling question instead, or nothing at all.
  2. Can't tell whether docs exist? → Ask. "Are there docs covering this?" is a better first question than any of the ten you were about to ask.
  3. No docs, or the docs aren't clear enough? → Go extensive.

Why the gate exists: a question already answered in the docs is a cost, not a courtesy.

"Keep interviews small and rare" and "make it a very detailed interview" are both right advice — the docs are what decides between them. Where a client has already handed over a detailed requirements list, the shape of the solution is settled and reviewed; interviewing around it burns attention and signals you didn't read it. Where there's nothing written, or the rules are the product and getting them wrong is expensive, go exhaustive.

The docs are the variable, not the appetite. Don't read "interviews should be small" as a universal — read the docs first and let them decide.

Before you ask anything

Research first. Every question you can answer yourself, answer yourself. Read the docs, the source material, the code. Done properly this collapses the question count — read the client's requirement PDFs and a ten-question list becomes "now the one real question before drafting." Unresearched questions are the ones that get ignored.

State your understanding before asking. Open with what you think you know:

"Here's what I understand before we start: ..."

It lets the person correct your frame in one sentence instead of discovering the misread six questions later.

File what you verified; ask only what you couldn't. A verified bug — one you traced, one you can point at the line for — gets filed as an issue, not raised as a question (no tracker? it becomes its own markdown file under issues/, one per bug — see /scoping). Escalate decisions, not findings. Don't make the person triage.

What makes a question land

The mechanism is subtler than "broad questions fail, narrow ones work":

When the answer depends on context you haven't discovered, your options get overridden. When it's a genuine design fork you've fully characterized, people pick clean — usually the one you recommended.

Tag your recommendation. On a genuine technical fork you've characterized — "Polars only for now", "process, not pipeline" — a (Recommended) pick is usually just taken. That's the cheap case, and it costs the reader nothing.

The expensive case is the other one: a question gets a paragraph of free text instead of a pick almost always because the answer lived somewhere you couldn't see.

Watch for picked-but-qualified answers too: "Agent-centric, but with the more granular view." A pick is not full agreement. Read the qualifier.

The out-of-repo escape hatch — the #1 failure mode

The classic shape: you offer four options on how the app should exchange data with the optimizer, or how auth should work, or where it deploys. Every option is reasonable. Every option is wrong — because the real answer is infrastructure only the person knew existed: an internal optimization-run platform (AIR), Keycloak, the internal deploy pipeline. None of it was inferable from the repo, so no amount of careful option-writing was going to land it.

Before offering a multiple choice, ask yourself: could this answer depend on something outside this repo? If yes:

  • Ask it openly instead, or
  • Add an explicit option: "something already exists here that I don't know about."

And group those questions under the header the agent itself eventually invented:

"AIR platform state (I can't see this from the repo)"

That header is the fix. It tells the person exactly which questions only they can answer, and stops you from dressing up a knowledge gap as a design choice.

Don't offer the wrong axis

One batch offered a build-effort axis — "real rule engine" vs "demo-illustrative only" — when the person cared about a product-meaning axis. He rejected the framing outright: "think of measures that will guide a planner instead of evaluation." If the answer comes back rejecting your options rather than choosing between them, you offered the wrong axis. Re-ask; don't push.

Question craft

  • State your instinct and label it. "My instinct: X — but it's your call." / "That's my read... I want it confirmed rather than assumed." This is the highest-yield habit here: it turns a question into a one-second confirmation. "I agree with your read" is a much cheaper reply than a paragraph.
  • Name the conflict, with evidence, inside the question. Spell it out: *"the client PDF never uses this term... the DB schema uses it for a per-day row... your rule 1 uses it for the multi-day concept... all three meanings are live right now."* The person never has to reconstruct why you're asking. Questions like this get answered fully and without pushback.
  • Say what the answer unblocks. *"This decides whether the module needs incremental recompute machinery at all."*
  • Number them and group by theme. Numbered questions earn numbered replies — every time, including rejections. Someone rejecting most of your list, each with a reason, is a good outcome: the format invited the correction instead of burying it.
  • Rank your own blockers. "Those three change the issue list's shape the most."
  • Surface assumed constraints. "I'm treating X as a hard constraint — correct me." The costliest corrections are always assumptions that were never raised as questions: a module structure proposed as settled and then rewritten wholesale (*"I would organize things a lit bit differently"), or an assumed data-preservation constraint that was never real ("There isn't an issue with loosing data to achieve that"*). Neither cost anything to ask about. Both cost a branch to discover.

Tool or prose?

  • AskUserQuestion for closed scoping forks you've fully characterized. Cap at 4 questions. Tag your recommendation (Recommended).
  • Free prose for open domain modeling — thematically grouped under bold headers. Prose batches can run longer than four, but only after deep document research has earned them.

Run it in rounds

Don't fire everything at once. Run 2–3 rounds of ~4 questions, and open each round by summarizing what the last one locked:

"Round 1 captured the spine. Round 2 — pinning the AIR contract."

Rounds keep people engaged rather than exhausted, and an engaged person volunteers constraints you didn't know to ask for. That's the real return: not the answers to your questions, but the things offered up after them.

Mid-task ambiguity flips the order

If you spot the problem — an ambiguity, a risk, a fact that doesn't add up — don't ask a bare question and don't quietly guess. Write up a short spec capturing the context first, then interview about that specific point. The context is what makes the question answerable.

When an answer contradicts the docs — stop and reconcile

The docs are the source of truth. So the moment something contradicts them, the docs have a bug in them — and you've just found it.

This happens constantly in a real interview: the answer you get contradicts a doc, two docs disagree, or the code does something the docs say it doesn't. Never silently pick a winner. Not the newest input, not the doc, not the code. Silently picking is how a source of truth quietly becomes a pile of claims — and the next person reads the doc, not this conversation.

What to do, every time:

  1. Stop and say so, immediately. Don't bank it for later; later is when you've already built on it.
  2. Quote both sides, with locations. *"docs/<file>.md says X. You've just said Y. Both can't be true."* Don't paraphrase — paraphrase is where the contradiction goes blurry and people agree to different things.
  3. Ask which is authoritative — and whether the other is stale, wrong, or describing something genuinely different that's been given the same name.
  4. Fix the doc as part of this work, in the user's own words, once they've ruled. Not a follow-up issue. Not "we should update the docs at some point."

The shape to watch for: three definitions of the same word live at once — the client's document, the database schema, and the rule you were just told, all using it differently. Surfaced as a question ("all three meanings are live right now — which one wins?") that's an immediate ruling and a docs cleanup. Guessed at, the ambiguity ships into the schema, where it costs a migration instead of a sentence.

Terminology collisions are the most common form and the easiest to miss — the same word meaning different things in two places reads as agreement right up until it doesn't. When you notice a word carrying two meanings, that's a contradiction, even though nothing looks wrong.

Never leave a known inconsistency in the docs. If it's genuinely unresolved, it goes in as an explicit open question with both readings written out — not as silence, and never as one reading presented as settled.

Output

Answers don't live in the chat. They land as:

  • Numbered requirement IDs in the docs, folded in alongside what's already specified — not a parallel document.
    • Functional (FR-<AREA>-<n>) — what the system does. If a user could watch it happen,
    it goes here.
    • Non-functional (NFR-<AREA>-<n>) — how well, how fast, how safely, built with what.
    • Keep them in separate files. Merging them "for now" is how performance and security
    quietly become optional — nobody reads "…and it should be fast" tacked onto a feature bullet. Same feature usually produces one of each.
    • New to the distinction, or unsure where something goes? → references/README.md.
  • A proposed cut table — what to drop, and why (see /review-gate's YAGNI ladder). Propose cuts against the numbered requirements, not against a hypothetical ideal system.

If there are no docs to fold into — which is the usual case when the mode gate sent you here — don't invent a shape. Start from references/docs-bootstrap.md: four files earn their keep on day one (scope-and-goals, functional, non-functional, architecture), and the rest get created when the project earns them. An empty doc is worse than a missing one; it looks like an answer.

Every M (must-have) requirement should be answerable by a test. If you can't imagine the test, the requirement is still too vague — fix it now, while it's a sentence and not a sprint (/test-design).

What comes out is an executable spec — good enough to turn straight into a pre-written failing test suite and build against module by module until it goes green. At that point the tests are the spec, not documentation of it.

Anti-patterns

  • Interviewing about something the docs already answer.
  • Asking before researching — every unresearched question spends someone's attention.
  • Offering four reasonable options when the real answer is infrastructure you can't see.
  • Presenting your instinct as a settled decision instead of labeling it as a read.
  • Taking an answer that contradicts a doc and just... using it, leaving the doc wrong.
  • Letting the same word mean two things because nobody said it out loud.
  • Firing 11 questions at once with no themes, no numbers, and no ranking.
  • Reading a (Recommended) pick as full agreement when it came with a qualifier.
  • Guessing silently on genuinely open scope, then discovering the assumption in review.

Templates for turning interview answers into documentation someone else can build from.

Functional requirements are what the system does — behaviours a user could watch happen. "The planner shall filter the schedule by date."

Non-functional requirements are how well it does it, and what it's made of — qualities and constraints. "Filtering shall feel instant." "Secrets come from environment, not source."

Same feature usually produces one of each. They live in separate files, on purpose — see "Why split them" below.

Why split them

Not tidiness — a failure mode. Merged, the non-functional ones get skipped. Nobody reads "…and it should be fast" tacked onto the end of a feature bullet, so it isn't designed for, isn't tested, and surfaces when the demo is slow in front of the client.

They're also read at different times by different people. Functional requirements get walked through in a demo. Non-functional ones get checked at review, at deploy, and at 2am. A file each means the second list actually exists.

When it's genuinely ambiguous

The taxonomy is fuzzier than most write-ups admit. "The screen shall be mobile-friendly" is a quality — but if it's true of exactly one screen, it belongs with that screen's functional requirements, not marooned in a global UX section where nobody building that screen will read it.

The rule of thumb: put it where the person who has to satisfy it will read it.

  • Global (applies across the system, or nobody owns it) → non-functional.
  • Scoped to one feature → with that feature, functional.
  • Genuinely both → write both, and cross-reference. That's not duplication; the feature-level one is the instance, the global one is the rule.

What actually matters is that it's written down once, somewhere it'll be checked. Don't spend an interview arguing the taxonomy — that's a question the docs can answer later, and a requirement in the "wrong" file still gets built. A requirement in neither file does not.

The NFR categories people forget

Non-functional requirements are the ones nobody thinks to ask about. Walk the list — most will be "not applicable", and the two that aren't are why you walked it:

Stack · Architecture & integration (the seams) · Performance & scale · Security & access · Deployment & operations · Internationalization · Usability & UX · Accessibility · Observability (logs, traces, how you'll debug it live) · Data retention & privacy · Compliance

For each: is it a real requirement here, or deliberately out of scope? Both answers go in the file — "Full RBAC and audit logging are out of scope (future)" is a decision. Silence is an omission, and only one of those survives a client meeting.

The rules

IDs are stable and permanent. FR-DATA-6 means one thing forever. Never renumber to close a gap — a retired requirement gets struck through or marked removed, not recycled. The ID is what issues, change requests, and tests point at; renumbering silently re-points all of them.

One requirement per row. If it has an "and" joining two testable things, it's two rows. The tell: you can't tick it off without saying "well, half of it."

Use "shall", and name the actor. "The planner shall…", "The system shall…". Not "should", not "we want to". shall is a commitment; should is a hope, and hopes don't get tested.

Write it observable. Someone must be able to sit down and check it without asking you what you meant. "The system shall handle errors gracefully" is not a requirement — it's a feeling. "A failed run shall surface an error reason to the planner (verbatim string; no error taxonomy)" is a requirement: you can look at the screen and see whether it's true.

Priority is a real decision, not decoration. M = the thing is broken/pointless without it. S = clearly wanted, survives a bad week. C = drop first, and expect to. If everything is M, you haven't prioritised — you've just written M forty times, and the first schedule squeeze will make the call for you, badly.

Record the cut, don't delete it. When something is dropped, say so in place with one line of why. A requirement that vanishes silently gets re-proposed in six weeks by someone who wasn't in the room.

Cite what governs it. Link the rules doc, the data model, the client source, the issue. A requirement that cites nothing is a claim.

Bold the load-bearing words. These get skimmed. **28-day window**, **idempotent**, **never exposed to the browser** — the bold is what survives the skim.

Where requirements come from, and where they go

interview / client docs  →  FR-<AREA>-<n>  →  issue (cites the FR)  →  change-request test plan  →  test

That chain is the whole point of the ID. Concretely:

  • /scoping — an issue names the FR it implements. "Implements FR-RUN-4" beats a paragraph.
  • /test-design — every M requirement should be answerable by a test. If you can't imagine the test, the requirement is too vague — fix it now, while it's a sentence.
  • /good-mr — the change request closes the issue and reports the test back.

If you can't trace a line of code to an FR, ask why it exists (/review-gate, rung 1 of the simplicity ladder: does this need to exist at all?).

Refining an existing set

Answers fold in; they don't start a parallel document. A new fact from an interview becomes a new numbered row in the area it belongs to. A second requirements doc is how a project ends up with two sources of truth and no way to tell which won.

A contradiction is a bug in this file. If an answer contradicts a row, don't just add the new one — flag it, get a ruling, and fix or strike the old row. Two rows that disagree are worse than one row that's wrong, because the wrong one at least loses arguments. See /extensive-interview ("When an answer contradicts the docs").

Propose cuts against the numbers. "Cut FR-RUN-9 and FR-KPI-5" is actionable. "Simplify the run flow" is a conversation you'll have three more times.

Anti-patterns

  • Renumbering to close a gap after a requirement is dropped.
  • should/could where you mean shall — or shall where you mean "it'd be nice".
  • Everything marked M.
  • Requirements nobody could test without asking you what you meant.
  • Two testable things joined by "and" in one row.
  • Non-functional requirements smuggled in as functional ones ("shall load quickly").
  • A second requirements doc, because editing the first one felt harder.
  • Deleting a cut requirement instead of recording the cut.

The rules

The Note column is where the honesty lives — use it. It records why a constraint is what it is, and what you deliberately gave up. "Not sized for 2,100 crew." "Replaces the scaffold's Postgres assumption for the demo." "Full RBAC out of scope (future)."

This is what stops the two failure modes that kill NFRs:

  • Someone reads a relaxed NFR as an oversight and "fixes" it, gold-plating a demo.
  • Someone reads it as a promise and ships it to production at 40× the scale.

An empty Note on a deliberately-relaxed requirement is a bug in this file.

Write the constraint you'd actually defend. "The demo shall handle ~49 agents × 28 days responsively. Not sized for 2,100 crew." — that's a real boundary you can hold. A hard SLA you invented ("p95 < 200ms") is a number you'll either ignore or be beaten with. Don't write one you don't mean.

Qualitative is allowed — say so. "Read screens shall render responsively on the seeded dataset. Qualitative — no hard SLA for a demo." That's more honest than a fake threshold, and more useful than silence.

Out-of-scope items belong here, written down. NFR-SEC-4: Full RBAC, audit logging, and override history are out of scope (future). This is not a confession — it's the difference between a decision and an omission. An omission gets discovered in a client meeting; a decision gets pointed at.

A named tool choice is a hard constraint, not a suggestion. Once NFR-STACK-3 names the table library, that's the answer — including for a reviewer who prefers another one. If the choice deserves to change, change this row first, then the code. Not the reverse.

Performance rules earned from real incidents are the best rows in the file. When you find a real trap — a request waterfall, an N+1, a lock — write it as an NFR with the evidence in the Note. It stops the next person re-finding it the expensive way.

Refining an existing set

  • New constraint from an interview → a new numbered row, in the area it belongs to. Not a new document.
  • A contradiction is a bug in this file — flag it, get a ruling, fix the row. See /extensive-interview.
  • Watch for functional requirements drifting in here ("the planner shall see a chart") and send them to the FR file. The drift usually goes one way: someone writes a UX requirement, then hangs behaviour off it.

Anti-patterns

  • An SLA number you invented and don't mean.
  • A relaxed requirement with an empty Note — indistinguishable from an oversight.
  • "The system shall be secure / fast / scalable." Not requirements. Feelings.
  • Out-of-scope decisions living only in someone's memory.
  • Letting a code review override a stack choice this file already settled, instead of changing this file.
  • Functional behaviour smuggled in under UX.
  • Skipping this file because the project is "just a demo" — the demo is exactly where the relaxations need writing down, because that's where you're making them.

The rules that make docs worth having

Docs are the source of truth, not a description written afterward. The order is: settle it in the doc → build to it. Not: build it → describe it. A divergence is a bug to reconcile, not a judgment call the implementer makes alone.

Number the docs and the requirements. # 2. Functional Requirements, FR-DATA-6. Numbers are what issues, change requests, tests, and questions point at. Prose has nothing to point at, so people paraphrase it, and paraphrases drift.

Update them in the same change as the code. Not a follow-up issue. A doc describing last week's behaviour is worse than no doc: it's a confident lie, and it gets believed.

Overclaims are more dangerous than omissions. A doc saying "this is index-backed" when it isn't will send someone down a day-long dead end. A doc that's silent just sends them to the code. Check both directions when you review (/review-gate lens 2).

Record decisions where the decision lives — next to the thing it governs, not in a parallel ADR tree (/teach-me, mode 3).

Never leave a known inconsistency. If two docs disagree, that's a bug — flag it, get a ruling, fix it. If it's genuinely unresolved, write both readings into "Open items", never one presented as settled.

Anti-patterns

  • Creating the full folder structure on day one, with nothing true in most of it.
  • A README.md that's prose instead of a table of contents.
  • Merging functional and non-functional requirements "for now".
  • Prose where an ID would do — nothing to cite, so nothing gets cited.
  • Docs written after the code, describing whatever the code happened to do.
  • Deleting a resolved open item instead of recording how it resolved.
  • A source file swapped without a note saying what changed and when.
  • Writing "What this is" and skipping "What this is NOT".

Before you build

/scoping

Turn a rough ask into an issue an agent can pick up cold.

A well-scoped issue is one an agent can pick up cold and execute end to end, without coming back to ask you anything. That is the bar.

Getting there is mostly research, not conversation. The questions you ask are what's left over after you've answered everything you could yourself.

The flow

  1. Read the docs. Not after — first.
  2. Answer everything you can from the docs and the code.
  3. File the verified bugs you found on the way. Don't ask about them.
  4. Ask only the genuine delta — the unknowns research cannot close.
  5. Write the issue, citing real files and specifying the tests.

1. Read the docs first

Docs are the source of truth. Before you scope anything, read the docs covering the area you're touching — the route table, the component list, the implementation contract, the data model, the rules doc. Whatever exists.

Cite the requirement, not a paraphrase. If the project has numbered requirements, the issue names them: "Implements FR-RUN-4" beats a paragraph restating it, and it makes the chain traceable end to end:

FR-<AREA>-<n>  →  issue (cites it)  →  change-request test plan  →  test

If you can't find a requirement your change serves, that's worth a beat: either one is missing, or the change is (/review-gate, rung 1 — does this need to exist at all?).

If there are no docs at all, don't quietly proceed on vibes and don't write the missing docs yourself mid-scope. Say so, and pick deliberately: for a genuinely small change, note the absence in the issue and cite the code instead. If the area is big or contested enough that the absence is why it's hard to scope, that's the signal for /extensive-interview and references/docs-bootstrap.md over there — not a bigger guess.

A question already answered in the docs is a cost, not a courtesy. It burns the reviewer's attention on something they already wrote down, and it signals you didn't look.

This cuts the other way too: if the docs are clear, the design is settled. Don't reopen it as an open question just because you'd have done it differently. A divergence between the docs and what you want to build is a thing to reconcile explicitly, not to quietly decide alone.

If something contradicts the docs, flag it — don't route around it

Scoping is where contradictions surface, because it's the one step that reads the docs and the code together. You'll hit these:

  • The code does something the docs say it doesn't. (Often the docs were right when written.)
  • The ask contradicts a documented decision.
  • Two docs disagree, or the same word means two different things in two places.

Don't route around it. Don't file the issue against what the code happens to do and leave the doc lying, and don't file against the doc and let the implementer discover reality on their own. Both bury the problem in someone else's afternoon.

Instead:

  1. Flag it to the user before filing, quoting both sides with their locations — *"docs/<file>.md says X; <file>.py:120 does Y. Which is right?"* Quote, don't paraphrase.
  2. Let them rule. Which is authoritative, and is the other stale, wrong, or a different thing wearing the same name? It's their call, not yours — and it's usually a ten-second answer.
  3. Then fix the doc, in the same breath as filing the issue. If the doc was wrong, correcting it is part of the work — put it in the issue's scope explicitly, so it can't be dropped.

Never leave a known inconsistency in the docs. A doc with one known-false line in it isn't a source of truth anymore — it's a thing everyone has learned to double-check, which costs more than having no doc at all. If it's genuinely unresolved, it goes into the issue's ## Open questions with both readings written out, not into silence.

The cheap tell you're routing around one: you catch yourself writing "the docs say X, but actually…" anywhere in the issue. That "but actually" is a doc bug you just decided not to fix.

2. Research collapses the question count

Every question you can answer yourself, answer yourself.

Read the client's requirement documents before scoping an offline-mode feature and a ten-question list collapses to one: "now the one real question before drafting." That's the shape to aim for. The research does the work the interview would otherwise have done badly.

The inverse is the tell: a long question list usually means shallow reading, not thoroughness.

3. File bugs, don't ask about them

If your research turns up a verified bug — you traced it, you can point at the line — file it as its own issue and move on. Don't put it in the question list.

File them, and the questions you do ask come back answered cleanly and in full — because none of them are triage the reader could have done themselves.

Don't make the user triage. Escalate decisions, not findings.

4. Ask only the genuine delta

When you do ask:

  • Four questions maximum if you're using an options prompt. Longer thematic lists are fine in prose, but only after deep research.
  • Number them. Numbered questions earn numbered answers, every time — including rejections.
  • Group by theme, with a bold header per group.
  • Name the conflict inside the question, with evidence. Never make the reader reconstruct why you're asking. "The client doc says X, the schema says Y, your rule 1 says Z — all three are live right now" costs you a sentence and saves them five minutes.
  • State your instinct and label it as yours. "My instinct: X — but it's your call." "That's my read, so I want it confirmed rather than assumed." This is the highest-yield habit in the whole skill: it converts a question into a one-second confirmation.
  • Say what the answer unblocks. "This decides whether we need incremental recompute machinery at all."
  • Rank your own blockers when you ask several: "those three change the issue's shape most."

The out-of-repo escape hatch

This is the single most common way scoping questions fail.

Before you offer a multiple choice, ask yourself: could the answer depend on infrastructure or context that doesn't exist in this repo?

The classic failure: you offer four options on how the app talks to the optimizer, or how auth works, or where it deploys. Every option is reasonable. Every option is wrong — because the real answer is infrastructure only the user knew about: an internal optimization platform, Keycloak, the internal deployment pipeline. None of it was inferable from the repo, so no amount of careful option-writing was ever going to land it.

So when the answer might live outside the repo:

  • Ask openly, not as a multiple choice, or
  • Include an explicit "something already exists here that I can't see" option, and
  • Label the group honestly: "<platform> state (I can't see this from the repo)". That header is the fix — it tells the reader exactly which questions only they can answer, and stops you dressing up a knowledge gap as a design choice.

Conversely, when you've fully characterized a genuine technical fork — two libraries, two architectures, and you understand both — a multiple choice with a labeled (Recommended) pick is exactly right, and gets picked cleanly.

Surface your assumed constraints

The costliest corrections are never the questions you asked badly — they're the assumptions you never surfaced at all. Two real ones:

  • An agent proposed a module structure as settled fact, never asking how it should be organized. The user rewrote it wholesale: "I would organize things a little bit differently."
  • An agent silently treated data preservation as a hard constraint. It wasn't, and had never been stated: "There isn't an issue with losing data to achieve that."

If you're treating something as fixed, say so: "I'm treating X as a hard constraint — correct me if not." An unstated constraint is invisible until it's cost you a branch.

5. Write the issue

Use references/issue-template.md as the skeleton and references/issue-exemplar.md as the worked example.

  • Title: Area: specific finding. State the finding, not the topic. Long and specific beats short and vague. *"Scenarios list page never refreshes run status — only opening a scenario re-checks it", not "Fix scenarios page"*.
  • Cite real files — the source file, the governing doc, and file.py:line where you can. An issue that names no file is a wish, not a spec.
  • Record decisions, park unknowns. ## Decision (confirmed) and ## Open questions are both honest. A placeholder issue should say it's a placeholder rather than fake a spec.
  • Say why this way, not just what. When you settled a fork — a package, a layer, a data structure — name the option you took and the one you rejected, one line each. This is the issue's teaching surface: the next person reads it as part of picking up the work, learns the trade-off for free, and doesn't reopen the decision in six weeks. See /teach-me — a couple of lines here is worth more than an essay nobody reads later.
  • Check the project's conventions before inventing any. Some projects define zero labels and zero milestones — in those, don't invent a taxonomy. List what the tracker actually defines before you reach for metadata (glab label list on GitLab, or the equivalent in your tracker's interface skill — see /using-glab for the GitLab one).

No tracker? Write the issue to a markdown file instead. Everything above still holds — the docs research, the citations, the test spec — it just lands as a file rather than a filed issue. Put each issue in its own file under a local issues/ directory (e.g. issues/<area>-<slug>.md), one file per issue — a bug you found on the way (step 3) is its own file, not an appendix to this one. The file is the spec an agent picks up; keep the same structure the template gives.

Specify the tests — this is the pattern worth stealing

Most issues never spec their tests. The ones that do are the ones that go right: when the issue names the boundary cases, the implementing change request reports back against exactly those cases. That mirroring is the most valuable convention in this skill, and it's rare because people forget it, not because it doesn't work.

Make it standard. Write the boundaries in the issue:

  • gap = 180min → "break" (exclusive lower bound)
  • gap = 181min → "rest_room"
  • gap = configured cap exactly → "violation"
  • a non-default cap (e.g. 200) shifts the boundary accordingly — proves it isn't hardcoded

That last line is the one that earns its keep: it specifies a test that catches a hardcoded constant, which the happy path never will. The change request then checks each case off by name.

See /test-design for what makes those cases good.

Anti-patterns

  • Asking a question the docs already answer.
  • Offering four reasonable options when the real answer is infrastructure you can't see.
  • Handing the user a list of findings to triage instead of filing them yourself.
  • An issue with no file citations — nobody can start from it.
  • Writing "the docs say X, but actually…" instead of getting the doc fixed.
  • Filing against what the code does and leaving the contradicting doc standing.
  • Inventing labels, milestones, or an assignee scheme the project doesn't use.
  • Leaving tests to the implementer's imagination when you know the boundaries.
  • Scoping a greenfield or architectural pivot as if it were a small change — that's /extensive-interview, not this.

Title: backend: compute + expose per-day break classification (break / rest-room / violation) for the Pairing Board

Why

GET /runs/{id}/pairing-board's TeamDay currently returns raw sos/eos/trips only. To align the Pairing Board with the pairing definition (see docs/pairing-planning-rules.md's "legal-but-costed band" and the pairing_engine rewrite's kpis.py/duties.py), the frontend needs to show, per in-day gap, whether it's:

  • a plain break
  • a rest-room booking (>180min, legal but costed — matches the existing restroom_bookings KPI's threshold, see seed/importer.py:376)
  • a hard-cap violation (>= max_daytime_break_min, currently seeded as 240 via the pairing.max_daytime_break_min run parameter, seed/importer.py:184 — configurable per run, not a fixed constant)

This classification is a business rule (and a configurable one) — it must not be duplicated/hardcoded client-side. It belongs in the backend.

Proposal

Extend the TeamDay schema (wherever PairingBoardResponse is assembled) with a computed breaks list per day — one entry per gap (SoS→first trip, trip→trip, last trip→EoS), each with:

  • start / end (HH:MM)
  • duration_min
  • kind: "break" | "rest_room" | "violation"

computed server-side from the run's actual configured max_daytime_break_min (and the 180min rest-room threshold), not a hardcoded value. Consider also exposing a per-day duty_span_min (EoS − SoS) if useful for a "duty span" display.

Reference

  • docs/pairing-planning-rules.md — "legal-but-costed band" (§ around lines 54-68)
  • pairing_engine/duties.py — canonical <240min hard cap / >180min rest-room definitions, kept deliberately distinct
  • services/kpi_service.py + seed/importer.py — existing (scenario-level, not per-day) restroom_bookings KPI computed the same way

Tests

  • Boundary tests for the classification, against the run's actual configured max_daytime_break_min (not a hardcoded 240):
    • gap = 180min → "break" (not "rest_room" — exclusive lower bound, matches the existing
    restroom_bookings KPI test)
    • gap = 181min → "rest_room"
    • gap = configured cap − 1min → "rest_room"
    • gap = configured cap exactly → "violation"
    • gap run with a non-default max_daytime_break_min (e.g. 200) shifts the violation
    boundary accordingly — proves it isn't hardcoded
  • Per-gap coverage: a day with SoS before the first trip's departure, a mid-day gap between two trips, and a gap between the last trip's arrival and EoS — all three gap positions must appear in breaks, each independently classified
  • Zero/one-trip days: a day with no trips (no in-day gaps to classify — decide & test whether breaks is [] or omitted); a day with exactly one trip (still classifies the SoS→trip and trip→EoS gaps if non-zero)
  • Overnight days: no trailing "last trip → EoS" break entry once EoS marks the start of the overnight stay (don't double-count that boundary as a break)

It cites everything. Two docs sections, three source files, and two of them with line numbers (seed/importer.py:376, :184). Nobody has to search. This is the single biggest difference between an issue an agent can execute and one it has to interview you about.

It belongs in the backend."* That paragraph exists to pre-empt the reviewer thinking this is a UI tweak. If you can predict the objection, answer it in the issue.

/test-design

Tests that tell you something you don't already know.

This is the part of the process that bends least. Everything else — architecture, naming, how a fan-out organises itself — is negotiable. Test discipline is not.

A test suite exists to tell you something you don't already know. Most of the ways tests fail are ways of quietly telling you nothing.

The one gate that never bends

A regression test is provably red before the fix and green after. Checked, not assumed.

No exceptions for "obviously correct" fixes. If you did not watch it fail, you do not know it tests the bug.

How to actually check it:

  • Write the test before the fix, or git stash the fix once it's written.
  • Run the test. Confirm it fails exactly as predicted — not for an unrelated reason (import error, wrong fixture, typo) that would also fail on correct code. A test that fails for the wrong reason is telling you nothing.
  • Restore the fix (git stash pop), run it again, confirm green.

A real case worth internalising: an agent reverted its own fix specifically to confirm the test failed as predicted, then re-applied it. That is the standard, not paranoia.

The subtle version of this failure: you replace an existing test. If a test used to assert pytest.raises(RuntimeError) and you swap it for something new, the new one must still fail on the old code. Otherwise it isn't a regression test, it's decoration.

Never reimplement the code under test

Call the real function. Always. There is one implementation, and the test imports it.

If the logic exists twice — once in the source, once in the test — the test is a tautology. It passes whenever the two copies agree, including when both are wrong, and it cannot fail for the reason you wrote it. You have not tested the code. You have tested that you can write the same bug twice.

It's the most damaging anti-pattern in testing because it's invisible: the suite is green, the coverage is up, and none of it means anything.

The four forms it takes

1. Copying the function into the test file. The blatant one. The copy is correct by construction and the real code rots freely behind it. Import it instead — always, even if the import is awkward.

2. Computing the expected value with the same algorithm. The common one, and the one that slips through review:

# WRONG — the test re-derives the answer the same way the code does
expected = sum(leg.duration for leg in legs) * RATE
assert compute_cost(legs) == expected     # passes even if RATE is wrong

# RIGHT — the expected value is a literal you worked out independently
assert compute_cost(legs) == 340.0        # 4h × 85/h, from the rate card

If your expected value is an expression that mirrors the implementation, you've written the function twice. Expected values are literals, or come from an independent source — the spec, the rate card, a hand-worked example, the client's own document. Work it out on paper, then hard- code it. A magic number with a comment explaining where it came from is better than a formula.

3. Reimplementing instead of loading, when the runtime is awkward. For a service worker, a bundled script, anything hard to import: load the real source into a sandboxed harness. It's more work than rewriting the logic, and it's the only version that tests anything.

4. Mocking so much the real code never runs. If every collaborator is a mock, the test asserts your mocks agree with each other. Mock the boundary — the network, the clock, the database — never the thing under test.

The check

If the implementation were deleted, would this test still pass?

If yes, it's testing a copy. Ask it about the expected values too, not just the call: if the implementation's formula changed to something wrong, would the expected value change with it and keep the test green?

This is /review-gate lens 3's sharpest question, and it's worth asking yourself before it gets asked of you.

Exact assertions, not vacuous ones

len(result.unstaffed) == 3 — not "the solve succeeded".

A test that asserts the code ran is a test that passes when the code is wrong. Assert the value, the count, the shape, the specific field. If the assertion would still hold after you break the feature, it isn't an assertion.

Meaningful coverage, not maximal coverage

Cover logic and interactive components. Do not cover trivial wrappers to move a percentage.

Write them during the build, not as cleanup after. Tests written afterwards are shaped by the implementation you already wrote; tests written alongside are shaped by the spec. The second kind finds bugs.

Coverage percentage is not a goal. "Every branch of this rule, both sides of this boundary, and the error path" is a goal.

Boundary specs — the highest-value pattern

When a rule has a threshold, spec the boundary from both sides and prove the value isn't hardcoded.

For a configurable threshold that classifies a gap:

  • gap = 180min → "break" (exclusive lower bound — the boundary itself, from below)
  • gap = 181min → "rest_room" (first value past it)
  • gap = configured cap − 1min → "rest_room"
  • gap = configured cap exactly → "violation" (the boundary from the other side)
  • **a run with a non-default cap (e.g. 200 instead of 240) shifts the violation boundary accordingly** — this is the one that proves the threshold is read from config, not baked in

That last case is the one people skip, and it's the one that catches a hardcoded constant.

Alongside the boundary, spec:

  • Every position the case can occur in — first, middle, last. A classifier that works on a mid-list element and breaks on the first one is a real bug that per-case tests miss.
  • Zero and one-element cases — and decide what the right answer is (empty list? omitted field?) rather than discovering it in production.
  • A consistency regression — when a new computation overlaps an existing one, assert they agree (e.g. the sum of the new per-day classifications equals the existing scenario-level KPI). This is what stops two implementations of the same rule drifting apart later.

Issue → change-request test mirroring

When the issue specs the boundary cases, the implementing change request's test plan reports back against exactly those cases. Same list, same order, ticked off.

This is the standard, not a nice-to-have. It makes the review mechanical: the reviewer diffs the issue's ## Tests against the change request's ## Test plan and any gap is visible without reading a line of code. If you're writing the issue, spec the cases (see /scoping). If you're writing the change request, answer them (see /good-mr).

Green is necessary, never sufficient

A passing suite is not evidence the feature works. Before calling it done, exercise the real thing: server up, job actually run, page actually loaded, output actually looked at.

If you claim you verified something, attach what you ran and what it printed. If you couldn't verify it, say so plainly — see /good-mr on disclosing what wasn't done.

Two questions to ask yourself before claiming done

  1. **"Is this just a workaround for the test to pass, or am I actually handling what the test should be covering?"** If you changed the test to match the code rather than the code to match the spec, stop.
  2. "What is the goal of this test?" If you can't say what it proves in one sentence, it isn't a test yet.

Changing a test is not the same as weakening one

Sometimes a test's premise becomes false by design — the feature legitimately changed. That's fine. Rewrite it, and say so explicitly, naming the premise that died and why.

Real precedent: a change request rewrote a test whose premise ("this endpoint never polls the upstream service") was now false by design, and explained that in the test plan. A reviewer could evaluate the decision.

What's not fine is loosening an assertion, deleting a case, or adding a skip to get to green. The difference is whether you can name the design decision behind it. If you can't, you're bending the test.

Structuring the suite

Portable shape — the specific libraries are an example, not the law:

  • Layer the tests. Router / service / repository (or equivalent) tested separately, so a failure localises. An integration test that's the only coverage tells you something broke.
  • Use a fake or in-memory stand-in when a test doesn't need the real database. Keep a real one for the tests that are actually about persistence.
  • Shared factories and helpers so tests build real fixtures instead of duplicating setup. Duplicated setup drifts, and drifted setup hides bugs.
  • Example instantiation: pytest + an async HTTP client + session-scoped temp-DB fixtures on the backend; Vitest + Testing Library + jsdom with shared factories on the frontend.

Anti-patterns

  • Claiming a regression test works without watching it fail on the old code.
  • Assertions that pass whether or not the feature works ("it returned something").
  • Writing tests after the build, shaped by the code instead of the spec.
  • Speccing a threshold's boundary but never a non-default value — the hardcoded constant survives.
  • Reimplementing the logic under test inside the test — in any of its four forms, and especially as an expected value computed the same way the code computes it.
  • Mocking the thing under test instead of the boundary around it.
  • Loosening an assertion or adding a skip to get green, without naming a design decision.
  • Chasing a coverage number by testing trivial wrappers.
  • Calling it done because it's green, without ever running the real thing.

Scope. Name the target, and hold one spelling for it:

  • underscore for code packages — backend, webapp, data_pipeline, solver_engine
  • hyphen for UI feature areas — search-panel, user-settings
  • comma-separate for multi — feat(backend,webapp):

Adopt whatever split your project already uses. The rule that matters is the next one.

Scope drift is a real cost. Spell the same package with an underscore in some commits and a hyphen in others and both stay readable — but together they make git log --grep lie to you. You search one spelling and silently miss everything filed under the other. Pick one spelling per target and never vary it.

Style. Imperative ("add", "fix", "stop", "drop", "replace"), lowercase after the colon, no trailing period.

Length: target ~70–72 characters, not the textbook 50. This is deliberate and counter-conventional. A 50-char cap forces vagueness; fix(pairing-board): stop overnight bar at next day's SoS, not its train is 71 characters and tells you the whole story. Take the room.

Exception to lowercase: when the first word is an identifier or proper noun, keep its real casing — fix(air): AIR_APP_ID was a typo, GET /runs lazily refreshes status.

Body — why first

Skip it only when the change is genuinely trivial. Otherwise, three paragraphs:

¶1 — the problem or root cause. Lead with the observed symptom, ideally the live one: "both seeded scenarios still showed 'Double rest days: 0' for every agent live". Then why it happens. Someone reading this in a year needs the situation, not your solution.

¶2 — the fix, and why this approach. Name the alternative you rejected — "instead of" is the phrase doing the work, and it's what turns a description into an explanation. State non-goals too, when you deliberately avoided a bigger change.

¶3 (optional) — consequences, and a Verified: line. Add an explicit Verified: note whenever "it works" isn't self-evident from the diff.

Bullets use - only. Never *, never 1.. Wrap at 72.

Pointing at the issue

Trailer on the last line of the body:

  • Closes #N — this commit resolves it
  • Refs #N — related, doesn't close it
  • Part of #N — one piece of a larger issue or epic

The Closes #N form is GitLab/GitHub's, the default flavor here. Jira reads smart-commit verbs against an issue key (Closes PROJ-123); Azure DevOps links with Fixes AB#123. Use whatever your tracker auto-links — the rule (one keyword, applied consistently, greppable) holds regardless of the token. If there's no tracker, point at the issue's markdown file by path.

Repeat the keyword per issue: Closes #61, Closes #62. Never Closes #61, #62 — the second number doesn't link.

Never Fixes #N. Closes is the convention. Pick one keyword and be consistent, so a reader can grep for it.

Subjects may also carry the reference inline: (#76) or (issue #84). Both are fine; the trailer is what does the linking.

If you're addressing a review comment rather than an issue, say so in the body and quote the claim you're responding to. "Addresses the review note about X" is a WHY that would otherwise be invisible.

The overnight bar extended to the next day's first trip departure, but

renders that SoS→train gap as its own break block -- so the bar drew

Stop it at SoS instead: mathematically identical to the break block's

break.left) directly, since a same-block position check can't catch a
neighboring block being overlapped.

The committed seed.db predates the double-rest reconstruction fix in
air_output_translation.py, so both seeded scenarios still showed
"Double rest days: 0" for every agent live, even after that fix
merged -- the fix only changes what NEW imports produce, not data

The workflow skills — /scoping, /good-mr, /review-gate, /delivery-loop — drive issues and change requests through whatever tracker your project uses; this skill is the concrete glab implementation of that role, and the default flavor in the examples throughout the pack. On GitHub, Jira, or Azure DevOps you'd reach for that tool's CLI (gh, the Jira CLI, az) the same way — the shape of the advice carries over; the specific flags below are GitLab's.

The meta-pattern

glab's flag semantics are inconsistent across subcommands, and most mistakes are gh-isms.

The same word means different things — or nothing — depending on the subcommand:

FlagWorks onFails on
--branchci statusci list (use -b)
--output jsonmr view, issue view, issue list, mr listmr diff
-alist — but it means assignee, not "all"anywhere you meant "all"
-missue noteissue close

The rule: run glab <sub> --help before porting a flag from a sibling subcommand or from gh. One --help call is cheaper than the three failed attempts it replaces. If you find yourself reasoning "well mr view takes --output, so mr diff must too" — stop and check.

Read the output, not the exit code

Most glab failures are soft. Pipe through 2>&1 — and you will, to capture the error — and glab's own errors exit 0, hiding in stdout. Check for a non-zero exit and you'll miss most real failures.

Read what came back. Don't infer success from the command not throwing. This bites hardest in scripts and loops, where a silent ERROR Unknown flag scrolls past and you "successfully" create nothing.

Auth: check, don't re-authenticate

Run glab auth status once at the start. Credentials persist across sessions (~/.config/glab-cli/config.yml), so authenticate only if it actually reports logged-out — then do it per your team's method for the host. Re-authenticating every session is a round-trip you don't need.

Tokens do expire, so the re-auth path is real. If auth starts failing, glab api personal_access_tokens/self shows expires_at, active, and revoked.

The seven that will bite you

Each of these costs multiple attempts if you don't know it. The fix is on the right.

1. --state does not exist — the most common

glab issue list --state opened
→ ERROR  Unknown flag: --state.

Fix: --opened / --closed / --all.

Do not "fix" it with -a all — -a is assignee:

glab mr list -a all
→ ERROR  Failed to find user by name: all.

For real state filtering beyond these, use glab api (below).

2. --branch on ci list

glab ci list --branch main
→ ERROR  Unknown flag: --branch.

Fix: -b main. Note glab ci status --branch main is fine. Same word, two subcommands, two answers — this is the meta-pattern in miniature.

3. -L is not --limit

glab issue list -L 10
→ ERROR  Unknown shorthand flag: 'L' in -L.

Fix: --per-page 10 (or -P 10).

4. You cannot close an issue with a comment

glab issue close 45 -m "Superseded by the new engine"
→ ERROR  Unknown shorthand flag: 'm' in -m.

A pure gh-ism — gh issue close -c exists, glab has no equivalent. Fix: two calls.

glab issue note 45 -m "Superseded by the new engine"
glab issue close 45

5. --description-file does not exist

glab issue create --title '...' --description-file ./issue.md
→ ERROR  Unknown flag: --description-file.

Fix: -d "$(cat ./issue.md)". There is no -F either.

6. mr merge refuses drafts

→ ERROR  This merge request is still a draft; run `glab mr update 62 --ready` to mark it as ready for review.

glab hands you the fix. It's a standing two-step:

glab mr update <n> --ready
glab mr merge <n> --yes

7. Guessed repo paths 404

glab issue list -R git.ltplabs.net/some-group/some-project
→ ERROR  404 Not Found.

Project paths are often deeper than you assume (several nested groups). Fix: omit --repo entirely when your cwd is inside the repo — glab resolves it from the git remote. If you must be explicit, hardcode it once:

REPO="<your-project-path>"   # full nested path, e.g. group/subgroup/team/project
glab issue list -R "$REPO" --opened -P 100

Do not derive it from the remote with sed — a regex that grabs the last two segments produces a wrong path on nested groups and 404s confusingly.

Passing descriptions: quoted heredoc

For anything multi-line, this is the idiom:

glab mr create \
  --title "perf(backend): fix request serialization under concurrent load" \
  --description "$(cat <<'EOF'

Summary

Closes #<n>. Requests were fully serialized because ...

Test plan

  • [x] Full backend suite — 261 passed

EOF )" \ --target-branch main --draft


**The quoting on `<<'EOF'` is load-bearing, not style.** Descriptions contain backticks, `$`,
and `#` — unquoted `<<EOF` expands them and you get a mangled body or a shell error.

For long or reusable bodies, write the file first, then `-d "$(cat file)"`. Never reach for
`--description-file` (see #5).

**`-y` / `--yes` is mandatory for non-interactive create** — without it `create` blocks on a
prompt nobody will answer until the call times out.

glab api is the escape hatch

Use it for exactly what the CLI can't express:

glab api "projects/:id/merge_requests?state=opened&per_page=20"   # real state filtering
glab api "projects/:id/pipelines?ref=main&per_page=3"             # pipelines by ref/sha
glab api -X POST "projects/:id/jobs/<job-id>/retry"               # retry a job
glab api -X PUT projects/:id/merge_requests/<n> -f title="..."    # un-draft / retitle

It's also the only way to merge with a custom commit message (glab mr merge can't set one) and to upload a file attachment.

Prefer the projects/:id/... shorthand — it auto-resolves from your cwd's git remote and is far less error-prone than URL-encoding a nested path (projects/group%2Fsub%2Fproject/...), which you only need from outside the repo.

It emits raw JSON — pipe it: | python3 -m json.tool, or | python3 -c "import json,sys; print(json.load(sys.stdin)['web_url'])".

Workflow patterns that hold up

  • Create → verify. After a successful create, immediately glab mr view <n> (or issue view). Don't trust the create's own output URL alone — it's the cheapest possible confirmation that what you meant to write is what landed.
  • Ready → merge. mr update --ready then mr merge --yes.
  • Batch reads in a shell loop: for n in 22 23 24; do glab issue view $n; echo "---"; done.
  • Check the label taxonomy before using one. Run glab label list. If the project defines no labels — many don't — don't invent a taxonomy. Track work in prose cross-references (Closes #N, Part of #N) instead. Don't add fields the project doesn't use.

Environment gotchas

  • _ZO_DOCTOR=0 — if you use zoxide, its "detected a possible configuration issue" banner prints ~7 lines before your real output on any cd-prefixed call, silently defeating head -n. Export it to shut the banner up.
  • status= is read-only in zsh. status=$(glab api ...) → read-only variable: status. Use job_status= / pstatus=. This bites specifically in CI-polling loops, where status is the natural variable name.
  • Cap polling loops. A for i in $(seq 1 20) loop with 10s sleeps exceeds the 2-minute command timeout and gets killed at Exit code 143. Keep total loop time under ~120s, or run it in the background.

A blocked merge is a decision, not an error

If a glab mr merge is blocked by a permission prompt or a policy classifier — stop.

Don't re-run the identical command hoping it passes, and don't reroute through glab api -X PUT .../merge to get the same effect by another path. Both have happened; both are wrong. The block is a human decision point, not a transient failure. Surface it and ask.

Anti-patterns

  • Porting a flag from gh, or from a sibling subcommand, without --help.
  • Trusting the exit code after 2>&1 instead of reading the output.
  • Re-authenticating at the top of every session "just in case".
  • Unquoted <<EOF for a description containing backticks or $.
  • --description-file / -F (they don't exist), or -a all (that's assignee).
  • Deriving the project path from the git remote with a regex.
  • Inventing labels for a project that has none.
  • Retrying — or rerouting around — a blocked merge.

/review-gate

The review that decides whether work is actually done.

An implementation agent reporting "finished" is a trigger, not a conclusion.

This skill runs the review that decides whether work is actually done. It is deliberately adversarial: the implementer's self-report is evidence, not proof.

When to run it

  • An implementation agent (or you) reports an issue is implemented.
  • Before opening a change request (MR/PR), and again before merging one.
  • Any time you're about to write "this is done" / "this works" / "tests pass".

Run it on every unit of work, every time. This instruction has a known failure mode: on long sessions it quietly lapses — the first few issues get reviewed, later ones don't, because nobody restated it. A lapse is a bug in the process, not an acceptable shortcut. If you notice it lapsed, the fix is to review the units you skipped, not to move on.

How to run it

Spawn a separate agent. The point is independence — an agent reviewing its own diff shares its own blind spots. Give the reviewer the diff and the original spec (the issue), not the implementer's summary of them.

Cheap, well-scoped fixes the review surfaces (a missing test, a doc overclaim) — apply directly. Reserve a fresh implementation agent for genuinely substantial follow-up.

The four lenses

Run all four. Most reviews check only the first and call it done.

1. Completeness — against the spec, not against "looks reasonable"

Re-read the original issue's acceptance criteria yourself. Do not trust the implementer's restatement of them. Ask: does this satisfy what was asked, or does it satisfy a drifted version of what was asked?

2. Doc accuracy

Docs are the source of truth, not paperwork written afterward. Check both directions:

  • Omission — does a doc still describe the old behavior?
  • Overclaim — does a doc assert something the code doesn't do? ("this is index-backed" when it isn't; "not yet set up" next to a suite that's clearly been running for weeks).

Overclaims are the more dangerous half, because the next agent builds against the doc. Weight them accordingly when the doc is a contract another team reads.

3. Test exhaustiveness — not "tests pass"

"Tests pass" is necessary, never sufficient. Ask:

  • Do the new tests cover the edge cases the issue implies, or only the happy path?
  • Is a regression test provably red before the fix and green after — checked, not assumed?
  • Are assertions exact, not vacuous? (len(result.unstaffed) == 3, not "the solve succeeded")

If a review claims "the tests would catch a regression here", trace that claim yourself. Don't take it on faith.

Hunt for reimplementation — the tautology check

Go looking for this one specifically; it doesn't announce itself. A test that reimplements its subject passes whenever the two copies agree, including when both are wrong. The suite is green, coverage is up, and none of it means anything.

For each new test, ask: if the implementation were deleted, would this test still pass?

Four things to actually look for in the diff:

  1. Is the real function imported and called? Or has a copy of it appeared in the test file?
  2. Where does the expected value come from? This is the one that slips through. An expected value computed by the same formula the code uses — expected = sum(l.duration for l in legs) * RATE — is the implementation written twice. It should be a literal, traceable to the spec or a hand-worked example.
  3. Is anything hard-to-import rewritten rather than loaded? A service worker or bundled script reimplemented in the test guards nothing.
  4. Is the thing under test mocked? Mock the boundary — network, clock, DB. Mocking the subject means the test asserts your mocks agree with each other.

This is a blocking finding, not a nit. A tautological test is worse than no test: it costs the same to maintain and buys a false sense of coverage, so nobody writes the real one.

See /test-design for the full rules this lens checks against.

4. YAGNI and simplicity

Two questions, not one:

  • Does the issue justify this code existing? No speculative abstractions, no generality nobody asked for, no scope creep past what was asked.
  • Is it simple to understand? Overly complicated logic is a defect in its own right, even when it's correct. If the same result is achievable in fewer lines, it should be.
The ladder

For anything being added, walk this ladder and stop at the first rung that holds:

  1. Does this need to exist at all? Speculative need → skip it, and say so in one line.
  2. Already in this codebase? A helper, util, type, or pattern that already lives here → reuse it. Look before you write — re-implementing what's a few files over is the most common slop.
  3. Stdlib does it? Use it.
  4. Native platform feature covers it? <input type="date"> over a picker lib, CSS over JS, a DB constraint over app code. Where the platform supports it, claim it — and say so explicitly ("used native X instead of adding Y" is a design decision worth recording).
  5. Already-installed dependency solves it? Use it. **Never add a new dependency for what a few lines can do.**
  6. Can it be one line? One line.
  7. Only then: the minimum code that works.
The rules around the ladder
  • Deletion over addition.
  • Boring over clever. Clever is what someone decodes at 3am.
  • Fewest files possible. Shortest working diff wins — but *only once you understand the problem*. The smallest change in the wrong place isn't lazy, it's a second bug.
  • Two options the same size? Take the one that's correct on edge cases. Lazy means writing less code, not picking the flimsier algorithm.

Reviewing against the ladder means naming the rung: "this reimplements a helper that already exists in <file>" (rung 2) is actionable; "this feels over-engineered" is not.

Verify the reviewer too

This is the part everyone skips. The reviewer is an agent, with the same failure modes as the implementer. Two failures worth internalizing:

  • A reviewer reported "2 pre-existing test failures, confirmed on main." Running the suite directly found 5 — plus a flaky 6th it never saw, which needed its own isolation pass to confirm it was non-deterministic rather than a real regression.
  • An automated review pass produced 6 findings; exactly 1 survived checking. Two were about a file the branch didn't even touch. One rested on the reviewer's own hedged guess.

So before you fix any finding:

  1. Confirm it's in this diff. git diff origin/main...HEAD -- <file>. If the flagged lines aren't there, the finding is about pre-existing code and is not yours to "fix".
  2. If the reasoning hedges, verify the premise. Words like if, likely, consistent with, presumably mark a guess. Check it with grep/read before acting on it.
  3. If it's about intentional-looking state on the main branch, ask before "fixing" it. Someone may have put it there deliberately, for reasons the diff doesn't show.

Findings that survive all three are usually real. Fix them in the same change request.

If the reviewer states a specific number or fact and it's cheap to check — check it before you repeat it to anyone. A number you pass along becomes yours.

Green is necessary, never sufficient

A passing suite is not evidence the feature works. Before calling it done, exercise the real thing: start the server, run the job, load the page, look at the output. If you claim something was verified, attach what you actually ran and what it actually printed.

If you couldn't verify something, say so plainly rather than omitting it. "Not verified from this environment" is a respectable line in a change request. A silent gap is not.

Reporting

Report findings ranked most-severe first, and for each: what's wrong, the concrete failure it causes, and whether you confirmed it or are flagging it as plausible. Separate:

  • Confirmed — you traced it and it holds.
  • Plausible — it looks wrong but you couldn't prove it; say what would settle it.
  • Not verified — you didn't check; say why.

Then state the verdict plainly: is this done, or not?

Write the review back to where the work lives — when there's somewhere to write it

A review that exists only in a session transcript is invisible to everyone who wasn't in that session, and gone by next week. If the work has a change request or issue in a tracker, post the review there. That's the traceable record: why this merged, what was checked, what wasn't.

On GitLab that's a note via glab (the default flavor):

glab mr note <n> -m "$(cat <<'EOF'
## Review — <verdict>
...findings, ranked...
EOF
)"

Use glab issue note <n> -m "..." when the work is tracked on an issue rather than a change request. On GitHub / Jira / Azure DevOps, post the same note through that tracker's CLI (see the tracker's interface skill). If there's no tracker at all, append the review to the markdown file the issue lives in (see /scoping) under a ## Review — <verdict> heading — same record, different medium.

"When there's somewhere to write it" is a real gate, not a formality. Skip posting — and say so in your summary — if any of these hold:

  • No change request, issue, or issue file exists yet (posting to nothing isn't traceability; open the change request first).
  • The tracker's CLI reports logged-out (glab auth status on GitLab), or the host is unreachable.
  • The work is purely local/exploratory and isn't going to any durable record.
  • The review contains anything that shouldn't be in a durable shared record: secrets, tokens, credentials, customer data. Scrub or omit — a comment is forever. Never paste a key into a note to "show the evidence."

Post the review before the merge decision, not after. A review posted after merging documents a formality; posted before, it's a gate someone can still act on. If the verdict is "not done", that comment is the reason the change request stays open.

Note that a note is not a merge. If a merge is blocked by a permission gate, that's a decision — post the review and stop; don't reroute to force the merge through another path.

See /using-glab for the GitLab note/heredoc mechanics and the glab api escape hatch — or your tracker's interface skill for the equivalent.

Anti-patterns

  • Taking the implementer's "all tests pass, docs updated" as the review.
  • Reviewing the summary instead of the diff.
  • Applying findings mechanically because they're labeled CONFIRMED.
  • Checking correctness only, and letting docs and tests through unexamined.
  • Counting the new tests instead of reading them — a tautological test looks like coverage.
  • Letting the review lapse on a long session because nobody restated it.
  • Calling work done because it's green, without ever running it.

/good-mr

An argument that a change is safe to land.

A change request is an argument that a change is safe to land, addressed to someone who wasn't there when you made it.

"Change request" is the tracker-neutral name for the reviewable unit — a merge request on GitLab, a pull request on GitHub / Azure DevOps. The command examples use glab as the default flavor; the mechanics for your tracker live in its interface skill (see /using-glab).

The reviewer's real question is never "what did you change?" — the diff says that. It's "what do you know that I can't see, and what don't you know?" Everything below serves that.

The shape

Two sections carry almost every change request: ## Summary and ## Test plan. Anything else is earned.

Summary ← Closes #N, then the user-visible effect, then bullets

Test plan ← real commands, real counts, unchecked boxes for what you skipped


For a bugfix, split the Summary:

Problem ← the symptom a user would report, then the mechanism

Fix ← what you changed and why this approach

Test plan


Use `references/mr-template.md` for the skeleton, `references/mr-exemplar.md` for a worked
example.

Titles

Two forms, and the split tracks size, not taste:

  • type(scope): imperative summary for surgical changes — the common case. fix(pairing-board): stop overnight bar overlapping the next day's break
  • Imperative prose (#N) for large ones — a migration, a rewrite, a multi-issue landing. Migrate pairing engine to integrated-MILP model + reconfig (issues #73, #82, #84)

A surgical fix under a grand prose title reads as overclaiming; a rewrite squeezed into fix(scope): reads as sneaking it past.

Scope is a package or feature area, not a layer. Titles are imperative: Add, Fix, Migrate, Remove, Store, Export. See /commit-message — the same convention governs both, and a merge commit's first body line is the change request's title.

Linking issues

Closes #N. goes on the first line of ## Summary, before the prose.

The Closes #N / !N syntax below is GitLab/GitHub's, the default flavor here. Jira uses smart-commit verbs and issue keys (Closes PROJ-123); Azure DevOps uses Fixes AB#123. Use whatever auto-links in your tracker — the discipline (link every issue, be explicit about partial work) is the same; only the token changes.

  • Repeat the keyword per issue. Closes #61, Closes #62, Closes #63 — never Closes #61, #62. Only the first one closes.
  • Scope partial work explicitly rather than letting it auto-close something it didn't finish: "Closes #76 (frontend half — the backend endpoint landed in !110, already merged)".
  • Part of #58, part of epic #60. when it closes nothing.
  • Reference sibling change requests as !N (GitLab) / #N (GitHub).

The Summary

Lead with the user-visible effect, not the implementation. "The scenarios list showed runs as still queued long after they'd finished" beats "refactored list() to call _refresh()".

Then bullets. Each one:

  • Cites the real symbol or path — RunService.list(), not "the service layer". Precision is what makes a reviewer able to check you.
  • Gives the why inline. Not in a separate design essay at the bottom; next to the thing.
  • Says which docs you updated, in the same change. Name the paths.

The Test plan

- [x] per check, each with a real command and a real count.

- [x] <full-suite command> — 398 passed - [x] <frontend test command> — 524/524 passing - [x] 5 new tests in <file> covering: <what each one proves>

Never write "tests pass". It's the single least useful sentence in a change request: it's unfalsifiable, and it's what someone writes when they didn't run them.

Name what each test proves, not that it exists. "covering: refresh progresses a run through to done via list() alone, a terminal run isn't re-polled, the status filter re-applies after refresh in both directions" tells the reviewer whether your coverage matches the risk.

Disambiguate pre-existing failures, and say how you proved it. Not "3 unrelated failures" — "3 failures, verified via git stash as present on main too", or "confirmed byte-identical to origin/main". The method is the point; the claim without it is just an assertion.

If the issue specified test cases (see /scoping), check them off by name. The issue said what agreement would look like; this is where you demonstrate it.

Disclose what you did not do

This is the heart of the skill. It's also the thing that most separates a change request a reviewer can trust from one they have to re-do.

Ship a deliberate unchecked box for anything you didn't verify. Not an oversight — a marker:

- [ ] Manual smoke test against a live deployment (not done from this environment) - [ ] A real, full run through the compute server has not been observed end to end — recommended before treating this as production-validated (see the caveat above).

An unchecked box is not a confession of sloppiness. It's the highest-value line in the change request, because it tells the reviewer exactly where to point their attention. A silent gap does the opposite: it looks complete, and the reviewer finds out in production.

Beyond the checkbox, invent the section the situation needs:

  • ## Scope (read before reviewing) — when the diff is bigger than the ask, and you want the reviewer oriented before they start.
  • ## Notable side effect — when your change moved something else's blast radius. *"This endpoint also calls list() — it will now additionally catch a run that finishes during that same request. Flagging so reviewers know its blast radius moved too."*
  • ## Verify-before-merge item (not blocking, but flagging) — a residual risk you investigated but couldn't fully close, with the reading behind it.
  • ## What's NOT in this change — the deliberate omissions.
  • ## Design decisions — the fork you took and why (see /teach-me).

Verify claims, don't relay them

When the issue, a comment, or another agent asserts something load-bearing — check it, and narrate the check:

"Verified, not trusted, one claim in the issue comment: it said the overnight count is 'already computed per agent in client_kpis()'. That file and function no longer exist in this tree..."

A claim you pass along becomes yours. If you couldn't verify it, mark it as unverified rather than laundering it into the Summary as fact.

Depth matches change surface

A big change request earns a big description. A trivial one doesn't need one — but even a one-liner carries its own evidence.

A perfectly good change request can be two sentences with no headings and no test plan, as long as it's purposeful: say why the change exists and link what it relates to. A one-paragraph change request that carries a single fact and the evidence for it — "A live test failed with a 404 at the assets endpoint, confirming that app id was never valid" — is complete.

The rule isn't "always write 2,000 characters". It's never assert without evidence, at any length.

Anti-patterns

  • "Tests pass." (Which tests? How many? Did you run them?)
  • Closes #61, #62 — closes exactly one issue.
  • A Summary that describes the diff instead of the effect.
  • Bullets that say "the service layer" when they could say RunService.list().
  • Quietly omitting the thing you couldn't verify, so the change request looks complete.
  • Relaying a claim from the issue as established fact without checking it.
  • Docs left describing the old behaviour while the change request describes the new one.
  • Padding a trivial change with ceremony — or shipping a substantial one bare.

Title: fix(backend): scenarios list refreshes AIR status too, closes #89

Closes #89.

Problem

RunService.list() (GET /runs, the scenarios list page) read runs straight from the DB and never called _refresh() — only RunService.get() (GET /runs/{id}, hit when opening a specific scenario) actually polled AIR, mapped status, and imported results once done.

The list's RunStatusChip looks like it's live-polling (useRunStatus revalidates every 4s), but that just re-runs the list loader — GET /runs again — which re-read the same stale DB row forever. A run that actually finished on AIR's side stayed queued/running on the scenarios list, results never imported, until a user happened to open that specific scenario's detail page.

Fix

RunService.list() now:

  • Fetches all runs, refreshes every non-terminal one (with an air_run_ref) concurrently via asyncio.gather — each _refresh() call already swallows its own transient failures (network hiccup, import error → marks that one run failed), so one slow/failing run can't block the rest or the list response.
  • Applies the status filter after refreshing, not before — a run whose status changes mid-call (e.g. queued → done) lands in the bucket it actually ended up in, not the one its stale pre-refresh DB row matched.

docs/backend/{routes,services-and-air}.md updated to describe GET /runs as a second lazy- refresh trigger alongside GET /runs/{id}.

Notable side effect

GET /runs/active/recompute-comparisons also calls RunService.list(status="done") — it will now additionally catch (and compare) a run that finishes during that same request, not just already-done ones. Consistent with the fix, flagging so reviewers know that endpoint's blast radius moved too.

Verify-before-merge item (not blocking, but flagging)

asyncio.gather now fires N concurrent AIR calls against the single shared AirpyClient/Air instance in AIR_MODE=air. Checked airpy's source: each get_run_by_id call opens its own aiohttp.ClientSession (no shared connection state), and the only shared mutable state is the auth-token cache (Auth.headers()) — worst case under concurrent refresh with a cold/expired token is a redundant duplicate login call, not corruption (Python's single-threaded event loop serializes the actual attribute writes). Considered safe for this app's scale (a handful of runs), but flagging since fixture-backed tests can't exercise the real AirpyClient path.

Test plan

  • [x] 5 new tests in test_services_run.py covering: refresh progresses a run through to done via list() alone (never get()), multiple non-terminal runs refreshed in one call, a terminal run isn't re-polled, a run with no air_run_ref is returned as-is, and the status filter re-applies after refresh in both directions (shrinks out of queued, appears in done).
  • [x] Updated test_api_runs.py's test_list_runs_status_filter_excludes_other_statuses, whose premise ("GET /runs never polls AIR") is now false by design — rewritten to make only one assertion-relevant poll against the fresh run, paired with the already-terminal seeded run for the exclusion-direction check.
  • [x] Full backend suite: 498/498 pass (<full suite command>).

Why this works

Symbol-level precision throughout. RunService.list(), _refresh(), RunStatusChip, useRunStatus, air_run_ref, asyncio.gather. A reviewer can jump straight to any claim and check it. Compare "the service layer doesn't refresh" — true, unverifiable, useless.

The Problem section leads with the user-visible failure. "A run that actually finished stayed queued/running on the scenarios list... until a user happened to open that specific scenario's detail page." You understand the bug before you understand the code.

It explains why the bug was invisible. *"The list's RunStatusChip looks like it's live-polling... but that just re-runs the list loader."* That sentence is why the bug survived — and it's exactly the thing a reviewer would otherwise ask about. Answering the unasked question is what makes a description feel trustworthy.

Rationale sits inline, next to the change. The asyncio.gather bullet explains in the bullet why one failing run can't block the rest. The filter-ordering bullet explains in the bullet why order matters (queued → done mid-call). No separate design essay at the bottom that nobody reads.

Docs updated in the same MR, and named. docs/backend/{routes,services-and-air}.md. Not "updated the docs" — which two files, and what they now say.

It volunteers a blast radius nobody asked about. The ## Notable side effect section flags that a different endpoint's behaviour moved as a consequence. The author found it, it wasn't strictly a bug, and they surfaced it anyway. This is the single strongest trust signal in the whole MR: it's evidence the author went looking for what else they'd touched.

It self-flags a residual risk — with the reading behind it. The ## Verify-before-merge item doesn't just say "concurrency might be risky." It says: I read airpy's source. Each call opens its own session. The only shared mutable state is the token cache. Worst case is a duplicate login, not corruption. Here's why the event loop makes that safe. But my tests can't exercise the real client path, so I'm flagging it.

That paragraph is what "not blocking, but flagging" should mean: investigated, bounded, and honestly bounded — not hand-waved. And it ends by naming the limit of its own evidence.

The test plan names what each test proves. Not "5 new tests added" — five behaviours, each stated. A reviewer can compare that list against the risk and see the coverage matches.

It discloses a test whose premise it invalidated. "test_list_runs_status_filter_excludes_other_statuses, whose premise ('GET /runs never polls AIR') is now false by design — rewritten to..." Changing an existing test is exactly where reviewers get suspicious. Explaining why the old test was now wrong turns a red flag into a demonstration of care.

/teach-me

Explain how and why, so people understand a little more each day.

The goal is not to answer the question. The goal is that the person asking needs to ask it less often next time.

Code that only its author understands is a liability, and an agent that explains nothing leaves the humans around it less capable every sprint. This skill is the counterweight: every artifact carries a little of the reasoning behind it.

When to run it

  • Someone asks you to explain something — explicitly, or by asking "why" or "how".
  • You're writing an issue or a change request — the rationale goes in, every time (modes 2 and 3).
  • You just made a non-obvious call — a package choice, a trade-off, a rejected alternative.

A "why" or "how" question is a teaching trigger, not a lookup request

These are all real questions from real sessions:

"How was it so fast?" · "are we using tuples and native python or polars?" · "what is the comm[p,t]?" · "How is the coverage created?" · "what are trechos?"

None of them wants a one-word answer. Each is someone building a model of the system in their head and finding a gap. Answer the question, then answer the question behind it — the thing they'd have asked next if they knew to.

Mode 1 — Inline explanation on demand

Socratic, and it doesn't end at your first paragraph.

The real shape, from a session where someone was reviewing a TypeScript change:

Them: "I am not really proficient in TypeScript, so can you explain in more detail?" You: (explains) Them: "But should the test fail if I go to that, or is that the behavior that you just put? What is the goal of this test?" You: (explains deeper — the actual point of the test, not just its mechanics) Them: "ok I think I understand a little bit better now, you can merge it."

Three things to take from that:

  1. Expect the probe. Invite it. The first explanation is never the last one. End with the thing they're most likely to still be unsure about, not with "let me know if you have questions."
  2. The probe is usually better than the original question. "What is the goal of this test?" is the real question. Treat a follow-up as a signal you explained the what and skipped the why.
  3. Understanding gated the merge. The change didn't ship until it was understood. That's the standard — not "it's correct, trust me."

Practical rules:

  • Never answer with just the mechanism. "It's memoized" is a fact. "It's memoized because the parent re-renders on every keystroke, and this recomputes a 13k-row aggregate" is an explanation.
  • Say what you'd have done otherwise, and why you didn't. The rejected alternative teaches more than the chosen one.
  • If they're not proficient in the language or the domain, say so out loud and adjust. Someone telling you "I am not really proficient in TypeScript" is giving you the level to pitch at. Use it.

Mode 2 — "Why this way" in issues and change requests

Every issue and change request carries a short rationale for the non-obvious calls in it, so people learn passively from artifacts they already read.

There's precedent to follow rather than invent — ## Design decisions in change requests, ## Decision (confirmed) in issues. Keep it to what's genuinely non-obvious:

  • Why this package and not the obvious alternative.
  • Why this shape — why the logic lives in the backend rather than the client, why the classification is computed rather than stored.
  • What you rejected, in one line.

Anti-pattern: a ## Design decisions section that explains the obvious. If the call was obvious, it isn't a design decision — it's just the code.

See /scoping and /good-mr for where these sections sit in the artifact.

Mode 3 — Durable decision records

Explanations that only exist in chat evaporate. Decisions that will still matter in three months go into the docs.

Fold them into the doc the decision belongs to — do not build a parallel ADR tree. A decision about the optimizer belongs next to the optimizer docs; a decision about the API contract belongs in the contract doc. The docs are already the source of truth; a second source of truth is just drift with extra steps.

What earns a record:

  • A decision someone will otherwise re-litigate ("why isn't this cached?").
  • A constraint that isn't visible from the code ("this is capped at 2 because the combinatorics explode above it — we tried").
  • A deliberate non-goal.

What doesn't: anything a reader can see by opening the file.

Mode 4 — Proactive teaching moments

Volunteer a short explanation when you make a genuinely non-obvious call, even if nobody asked.

Cap it at ~3 sentences. Non-obvious calls only. Never on routine work.

The cap is the whole point. Summaries get skimmed — that's a fact about how people read, not a failing. Unbounded proactive teaching fights the thing that makes delegation work in the first place: if every status update carries a lecture, the updates stop getting read, and the one that mattered gets skimmed with the rest.

Good:

Used the DB's own unique constraint rather than a check in the service layer — the service can't see concurrent writes, so an app-level check would pass and then still collide under load.

Bad: three paragraphs on the history of optimistic locking. Bad: explaining that you renamed a variable.

Writing for a mixed audience

These artifacts get read by people at very different levels. Assume the room.

  • Define jargon on first use — including domain jargon. If a term arrived from a client document in another language, define it the first time it appears and then use it consistently.
  • Prefer a worked example over an abstraction. One concrete case with real values beats a paragraph of theory.
  • Don't hide the hard part. If the tricky bit is the boundary condition, spend your words there, not on the setup.
  • Explain the package choice, not just the API call. "We use X" is trivia; "we use X because Y couldn't do Z, and here's what that costs us" is the thing worth knowing.

Anti-patterns

  • Answering the literal question and stopping, when the gap behind it was obvious.
  • Explaining the mechanism (what the code does) and calling it an explanation.
  • Treating a follow-up question as a nuisance rather than as evidence you under-explained.
  • A ## Design decisions section full of obvious decisions.
  • Building an ADR folder nobody reads instead of updating the doc that governs the thing.
  • Proactive teaching on routine work, until the summaries stop being read.
  • Merging something the reviewer said they didn't understand.

What these can’t do

A skill has to be invoked. It can’t fire itself when an agent finishes — that needs a hook, or a standing line in a project’s AGENTS.md. The known failure mode is that a standing instruction — review every unit, update the docs, exhaustive tests — quietly lapses on a long session. Treat that as a bug in the process, not an acceptable shortcut.
